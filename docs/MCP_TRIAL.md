# Anonymous MCP trial (`/mcp-trial`)

A no-login trial endpoint for ChatGPT and other MCP clients on the dedicated
MCP deployment. It is a separate, restricted MCP server. The authenticated
`/mcp` endpoint, its OAuth flow, token/resource/scope validation and every
existing check are unchanged: `/mcp` still answers an unauthenticated request
with HTTP 401 and a `WWW-Authenticate` header naming the protected-resource
metadata.

Implementation: `lofgren_intelligence/hosted/trial.py`. Tests:
`tests/test_mcp_trial.py`. Manifest: the `trial` section of
`docs/CAPABILITIES.json` (generated by `python -m lofgren_intelligence.hosted.capabilities`).

## Enabling it

The trial is off by default. It is mounted only when both are set:

- `LI_DEPLOYMENT_SURFACE=mcp`
- `LI_TRIAL_ENABLED=true` (`false` or unset disables it; any other value fails startup)

It also needs the Supabase store (`SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`)
with the existing `li_take_keyed_rate_limit` migration. Without a working store,
every trial request is refused (see below). No new migration is required.

## Tools

Only these tools are registered. All three are trial-only. None is listed on
`/mcp`, and no `/mcp` tool is listed on the trial.

- `trial_research` (trial-only): research one narrow factual question over one public source.
- `trial_verify_claim` (trial-only): verify one factual claim over one public source.
- `trial_compare` (trial-only): compare 2 to 4 named options. Bounded public-source research is followed by LI V2 discovery over that evidence (framing, gaps, connections, hypotheses).

Every call runs the real LI kernel. `run_investigation` produces the
research/verification graph, the verifier and the native research receipt.
`trial_compare` also runs `run_discovery` and returns its native discovery
receipt. The trial returns no static or canned answers. Each result includes,
inline:

- the findings summary and artifacts (the markdown report, full findings, contradictions and open unknowns)
- the native `receipt` and `receipt_intact`, plus the discovery receipt for comparisons
- provenance (sources, evidence, rejected evidence and the provider)
- the cost estimate, the applied bounds and the limitations
- `identity: "anonymous"` and `persisted: false`

Sources are Europe PMC (`source: "europepmc"`), ClinicalTrials.gov
(`"clinicaltrials"`), or the operator's manifest (`"operator"`). The operator
manifest is available only when the operator sets `LI_TRIAL_SOURCES_MANIFEST`
to an inline manifest of at most 1 entry. Callers cannot supply URLs,
manifests, inline documents or web search.

Reasoning uses LI's deterministic heuristic provider, so the trial incurs no
third-party model spend. The authenticated service may use a configured model
provider.

**Clarification is preserved.** The domain-aware Q23 classifier
(`requires_clarification`) runs on every trial objective. A consequential or
underspecified objective returns its clarification questions with
`approval_required: true` and `researched: false`. No research runs and no
spend is reserved. Serious work needs an Intelligence Case approved in the
browser, which requires a connected account.

## Security-scheme metadata (OpenAI mixed-auth convention)

Each trial tool declares `securitySchemes: [{"type": "noauth"}]` as a top-level
property of the tool descriptor in `tools/list`. The OpenAI Apps SDK
authentication guide (developers.openai.com/apps-sdk/build/auth, checked
2026-10-11) places the property there. The trial also mirrors it in
`_meta.securitySchemes`, alongside `_meta["li/trial_only"]: true`.

The MCP Python SDK's `Tool` model drops unknown top-level fields, so the trial
endpoint copies `_meta.securitySchemes` to the top level on JSON `tools/list`
responses.

This is a separate server, not a mixed-auth server. Its tools declare only
`noauth`. Authenticated tools stay on `/mcp`, behind its OAuth discovery.

*Assumption:* a protected tool name called on the trial returns an error
result that points to `/mcp`. The result does not carry
`_meta["mcp/www_authenticate"]`, because that challenge would point ChatGPT at
the trial connector itself rather than at the `/mcp` resource.

## What the trial does not do

- It does not identify users. Identity is always anonymous. An `Mcp-Session-Id`, a bearer token, a cookie or any argument the model supplies (`user_id`, `case_id`, `job_id`, ...) is never treated as identity. Trial requests bypass the `/mcp` bearer middleware, and their `Authorization` and `Cookie` headers are removed before the trial server sees them.
- It does not touch private Cases, runs, jobs, discoveries, artifacts, actions, usage reservations, entitlements or billing. The only store call the trial makes is the keyed rate limiter.
- It does not run durable jobs, external execution or any other consequential action. None of these exist on the trial.
- It does not keep history. Nothing about the question or its result is saved.
- Protected tools (every `/mcp` tool, and any unknown name) are refused with `ACCOUNT_REQUIRED`. The refusal names the `/mcp` resource to connect, and `_meta["li/account_required"]` carries the same pointer.

## Per-call hard bounds

These are constants in `TrialBounds`. Operators cannot raise them.

| Bound | Value |
|---|---|
| Public sources per call | 1 |
| Records retrieved | 5 |
| Source pages / logical fetches | 1, no retries; protected HTTP redirects may add network requests |
| Upstream request timeout | 10 s |
| Operator manifest entries | 1 |
| Request body | 16,384 bytes, read within 5 seconds |
| Active tool calls per process | 2, refused immediately when busy |
| Research plan tasks | 8 |
| Wall-clock time | 40 s cooperative deadline at stage boundaries and before delivery; not hard interruption |
| Output size | 256,000 bytes. The report, then full findings, then evidence detail are shed first. The receipt is never dropped; if the result still does not fit, the call is refused (`TRIAL_OUTPUT_BOUND`). |
| Estimated cost | $2.00 (LI platform-price estimate of the plan). A larger plan is refused before any work (`TRIAL_BOUND_EXCEEDED`). |
| Question / claim | 500 characters |
| Source query | 200 characters |
| Options (`trial_compare`) | 2 to 4, each up to 120 characters |

The time bound is cooperative and enforced at stage boundaries. It cannot interrupt an in-progress CPU stage or guarantee a 40-second response; hosted elapsed-time proof remains required. Per-process capacity stays occupied until that operation exits. Shared database admission/spend limits apply across instances, but the two-call concurrency cap is per process, not a distributed lease. Each fetch attempt uses a 10 s network timeout; DNS, redirects and streamed reads mean this is not a total wall-clock guarantee. The protected fetcher revalidates every redirect. Hosted worst-case duration still requires proof before enabling the trial.

## Abuse controls and the spending ceiling

All controls use the existing database-backed keyed limiter
(`li_take_keyed_rate_limit`), so they hold across serverless instances. All of
them **fail closed**. The trial always passes the store explicitly and never
uses the in-memory limiter, even with `LI_RATE_LIMIT_BACKEND=memory`. The four
buckets are listed in `FAIL_CLOSED_BUCKETS`.

| Control | Bucket | Default | Env override |
|---|---|---|---|
| Requests per client IP (HTTP, every trial request) | `trial_ip` | 30 / minute | `LI_TRIAL_IP_REQUESTS_PER_MINUTE` |
| Requests, global | `trial_global` | 600 / minute | `LI_TRIAL_GLOBAL_REQUESTS_PER_MINUTE` |
| Tool calls per client IP | `trial_call_ip` | 10 / hour | `LI_TRIAL_IP_CALLS_PER_HOUR` |
| Operator-wide spending ceiling | `trial_spend` | $10.00 / 86,400 s | `LI_TRIAL_SPEND_CEILING_USD`, `LI_TRIAL_SPEND_WINDOW_SECONDS` (60 to 86,400) |

Refusals:

- An HTTP limit returns `429 rate_limited` with `Retry-After`.
- A tool-call allowance returns `TRIAL_RATE_LIMITED`.
- An exhausted ceiling returns `TRIAL_CEILING_REACHED`, and nothing runs.
- A store that is unconfigured, unreachable or returns an invalid answer gives `503 temporarily_unavailable` at the HTTP layer, or `TRIAL_UNAVAILABLE` during a call.
- An invalid configuration value also gives `TRIAL_UNAVAILABLE`. A ceiling of `0` disables trial research.

**Ceiling accounting.** Each research call reserves the worst-case per-call
amount ($2.00) against the ceiling. The reservation happens after the plan
passes its bounds and before any work runs. The window therefore allows
`floor(ceiling / 2.00)` calls. A call that later fails still counts, so the
ceiling never under-counts. A clarification-only answer reserves nothing.
`LI_TRIAL_SPEND_CEILING_USD=10` therefore allows 5 research calls per window.

The client IP is the socket peer, or the header named in `LI_CLIENT_IP_HEADER`
when the host overwrites it. This is the same rule as the other per-IP limits.

## What is stored

Only rows in `li_rate_limit_events`, written by `li_take_keyed_rate_limit`:

- `bucket`: one of `trial_ip`, `trial_global`, `trial_call_ip`, `trial_spend`
- `key_hash`: SHA-256 of `"<bucket>:<key>"`, where the key is the client IP (per-IP buckets) or the constant `operator` (global buckets)
- `created_at`

Raw IPs, questions, results, session ids and tokens are never stored. Rows
outside their window are deleted on the next take for that key, and an
opportunistic prune removes any row older than one day.

*Limitation:* the IP digest is unsalted, as for the existing OAuth and
activation limits. IPv4 digests can be reversed by enumeration, so treat them
as personal data for at most one day.

Request telemetry is the existing content-free structured log line (method,
path, status, duration, request id). It contains no IP or body.

## How ChatGPT connects

1. Deploy the dedicated MCP surface with `LI_TRIAL_ENABLED=true` and a configured store.
2. In ChatGPT (developer mode, add a connector or app), enter `https://<mcp-origin>/mcp-trial` with no authentication.
3. ChatGPT initializes, lists the three `noauth` tools and can call them anonymously.
4. For Cases, durable research, history and the full tool set, connect `https://<mcp-origin>/mcp` with OAuth as described in `docs/PUBLIC_MCP.md`.

## Not verified

**The real ChatGPT installation test has NOT been done.** No ChatGPT connector
has been installed against `/mcp-trial`, and no ChatGPT session has called the
trial tools. The repository verifies the following only with tests:

- the HTTP and JSON-RPC behaviour
- the `securitySchemes` placement
- the bounds and the fail-closed abuse controls
- the real pipeline on fixtures

The current OpenAI documentation was consulted for the `securitySchemes`
placement. ChatGPT's handling of a separate noauth connector beside an OAuth
connector has not been observed. No hosted deployment of the trial exists.
