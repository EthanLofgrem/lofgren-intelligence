# Anonymous MCP trial (`/mcp-trial`)

A no-login trial endpoint for ChatGPT and other MCP clients on the dedicated
MCP deployment. It is a separate, restricted MCP server. The authenticated
`/mcp` endpoint, its OAuth flow, token/resource/scope validation and every
existing check are unchanged: `/mcp` still answers an unauthenticated request
with HTTP 401 and a `WWW-Authenticate` header naming the protected-resource
metadata.

Implementation: `lofgren_intelligence/hosted/trial.py` and the bounded upstream
fetcher `lofgren_intelligence/hosted/trial_fetch.py`. Tests:
`tests/test_mcp_trial.py` and `tests/test_mcp_trial_hardening.py` (fake upstream
servers on 127.0.0.1 only; no test reaches the public internet), plus the
real-PostgreSQL proof of the concurrency slots in `tests/pg/test_migrations_pg.py`.
Manifest: the `trial` section of `docs/CAPABILITIES.json` (generated by
`python -m lofgren_intelligence.hosted.capabilities`).

## Enabling it

The trial is off by default. It is mounted only when both are set:

- `LI_DEPLOYMENT_SURFACE=mcp`
- `LI_TRIAL_ENABLED=true` (`false` or unset disables it; any other value fails startup)

It also needs the following, or it refuses every trial request (fail closed):

- the Supabase store (`SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`) with the
  `li_take_keyed_rate_limit` migration and the forward-only
  `20261011120000_li_trial_slots` migration (global concurrency slots);
- `LI_TRIAL_IP_HMAC_KEY`: a secret of at least 32 characters, set only in the
  host's secret store, never in a file. It keys the per-IP digests (see below).

Nothing in this repository enables or deploys the trial.

## Tools

Only these tools are registered. All three are trial-only. None is listed on
`/mcp`, and no `/mcp` tool is listed on the trial.

- `trial_research` (trial-only): research one narrow factual question over one public source.
- `trial_verify_claim` (trial-only): verify one factual claim over one public source.
- `trial_compare` (trial-only): compare 2 to 4 named options. Bounded public-source research is followed by LI V2 discovery over that evidence (framing, gaps, connections, hypotheses).

Every call runs the real LI kernel. `run_investigation` produces the
research/verification graph, the verifier and the native research receipt.
`trial_compare` also runs `run_discovery` and returns its native discovery
receipt. The trial returns no static or canned answers. Each result includes,
inline:

- the findings summary and artifacts (the markdown report, full findings, contradictions and open unknowns)
- the native `receipt` and `receipt_intact`, plus the discovery receipt for comparisons
- `retrieval`: how the one source retrieval ended (`complete` or `partial`), the records kept and the upstream requests sent
- provenance (sources, evidence, rejected evidence and the provider)
- `cost`: the platform-price estimate and the infrastructure-cost estimate, kept apart (see "Cost policy")
- the applied bounds and the limitations
- `identity: "anonymous"` and `persisted: false`

Sources are Europe PMC (`source: "europepmc"`), ClinicalTrials.gov
(`"clinicaltrials"`), or the operator's manifest (`"operator"`). The operator
manifest is available only when the operator sets `LI_TRIAL_SOURCES_MANIFEST`
to an inline manifest of at most 3 entries. A call fetches **one** of those
pages: the entry whose title, publisher, note and URL best match the objective
(ties go to the first entry). Callers cannot supply URLs, manifests, inline
documents or web search.

Reasoning uses LI's deterministic heuristic provider, so the trial incurs no
third-party model spend. The authenticated service may use a configured model
provider.

**Clarification is preserved.** The domain-aware Q23 classifier
(`requires_clarification`) runs on every trial objective. A consequential or
underspecified objective returns its clarification questions with
`approval_required: true` and `researched: false`. No research runs and
nothing is reserved. Serious work needs an Intelligence Case approved in the
browser, which requires a connected account.

## Security-scheme metadata (OpenAI mixed-auth convention)

Each trial tool declares `securitySchemes: [{"type": "noauth"}]` as a top-level
property of the tool descriptor in `tools/list`. The OpenAI Apps SDK
authentication guide (developers.openai.com/apps-sdk/build/auth, checked
2026-10-11) places the property there. The trial also mirrors it in
`_meta.securitySchemes`, alongside `_meta["li/trial_only"]: true`.

The MCP Python SDK's `Tool` model drops unknown top-level fields, so the trial
endpoint copies `_meta.securitySchemes` to the top level on JSON `tools/list`
responses.

This is a separate server, not a mixed-auth server. Its tools declare only
`noauth`. Authenticated tools stay on `/mcp`, behind its OAuth discovery.

*Assumption:* a protected tool name called on the trial returns an error
result that points to `/mcp`. The result does not carry
`_meta["mcp/www_authenticate"]`, because that challenge would point ChatGPT at
the trial connector itself rather than at the `/mcp` resource.

## What the trial does not do

- It does not identify users. Identity is always anonymous. An `Mcp-Session-Id`, a bearer token, a cookie or any argument the model supplies (`user_id`, `case_id`, `job_id`, ...) is never treated as identity. Trial requests bypass the `/mcp` bearer middleware, and their `Authorization` and `Cookie` headers are removed before the trial server sees them.
- It does not touch private Cases, runs, jobs, discoveries, artifacts, actions, usage reservations, entitlements or billing. The only store calls the trial makes are the keyed rate limiter and the trial concurrency slots. `trial.py` and `trial_fetch.py` import none of the service, jobs, worker, billing, auth, entitlement or Case modules. One test parses their imports. Another runs every tool with the service, the token verifier and every other store method set to fail the test if touched.
- It does not run durable jobs, external execution or any other consequential action. None of these exist on the trial.
- It does not keep history. Nothing about the question or its result is saved.
- Protected tools (every `/mcp` tool, and any unknown name) are refused with `ACCOUNT_REQUIRED`. The refusal names the `/mcp` resource to connect, and `_meta["li/account_required"]` carries the same pointer. The trial lists no resources and no prompts.

## Per-call hard bounds

These are constants in `TrialBounds`. Operators cannot raise them. Each one is
enforced at runtime.

| Bound | Value | Enforced by |
|---|---|---|
| Public sources per call | 1 | the plan is refused (`TRIAL_BOUND_EXCEEDED`) if it uses more |
| Records retrieved | 5, from one page | adapter bounds |
| Upstream HTTP requests | **1 per call**, retries and redirects included | the `TrialFetcher` request budget refuses a second request before it is sent |
| Retries | 0 | the client runs with `max_retries=0`, and the budget would refuse a retry anyway |
| Redirects | 0 (refused, not followed) | `TrialFetcher`; the redirect target is never requested |
| Upstream body | 1,000,000 bytes | Content-Length is checked before reading, then the bytes actually read are counted (chunked and unsized bodies included) |
| Upstream connect and each socket operation | 10 s, or the time left if less | socket timeouts |
| Operator manifest entries | 3 listed, 1 fetched per call | `_pick_manifest_entry` |
| Research plan tasks | 8 | plan check |
| Wall-clock time of a tool call | 40 s, admission included | see "Time bound" |
| Output size | 256,000 bytes. The report, then full findings, then evidence detail are shed first. The receipts are never dropped; if the result still does not fit, the call is refused (`TRIAL_OUTPUT_BOUND`). | `_bounded_output` |
| Platform-price estimate | $2.00 per call. A larger plan is refused before any work (`TRIAL_BOUND_EXCEEDED`). | plan check |
| Question / claim | 500 characters | input check |
| Source query | 200 characters | input check |
| Options (`trial_compare`) | 2 to 4, each up to 120 characters | input check |

Tests count the requests that a fake upstream server on 127.0.0.1 actually
receives. Each tool sends one per call. An operator manifest of three URLs
gets one request. A 503 gets one request, with no retry. A redirect gets one
request, and its target gets none.

### Time bound

Stage-boundary checks alone cannot interrupt an operation that is already
running. The bound is therefore enforced in three ways:

1. **The response never outlives the deadline.** The whole call (per-IP
   allowance, admission, research, discovery and output) runs in a worker
   thread. The tool waits at most the time left (`_run_bounded`) and then
   answers `TRIAL_TIME_BOUND`, whatever the worker is doing. A test stalls the
   pipeline in non-network code for 4 s under a 1 s bound, and the refusal
   arrives in under 2.5 s.
2. **The upstream socket is closed at the deadline.** `TrialFetcher` sets the
   socket timeout to `min(10 s, time left)` and re-checks the deadline between
   16 KiB reads. A watchdog timer shuts the socket down at the deadline. Tests
   cut two servers at the deadline: one that never sends headers, and one that
   drip-feeds its body one byte every 50 ms, so that each read succeeds well
   inside the socket timeout.
3. **The worker stops.** At the deadline the call is cancelled. The next stage
   check in the worker raises, and the worker releases its concurrency slot.

**Worst-case wall time of one trial HTTP request: 50 s.** That is the 40 s call
bound plus the HTTP-level admission that runs before the MCP request is
handled: at most 2 store calls (the per-IP and global request limits), each
with a 5 s store timeout. It is under the 60 s function limit in
`vercel.json`. A test derives the 50 s from the constants and checks it
against `vercel.json`. After the response, the worker may still make one
slot-release call (5 s timeout).

## Cost policy

Every research call reports two different numbers. Neither is a measurement:
**an estimate is never a measured cost**, and LI does not meter the trial's
infrastructure cost.

- **Platform-price estimate** (`cost.platform_price_estimate`, bounded by
  `TrialBounds.max_estimated_usd`): what LI's pay-as-you-go price list would
  charge for the research plan. The trial charges nothing. The trial ceiling
  is counted in these dollars.
- **Infrastructure-cost estimate** (`cost.infrastructure_cost_estimate`): LI's
  cost to serve the call, from `hosted/costing.actual_run_cost` with the
  operator's configured rates (`LI_RETRIEVAL_USD_PER_CALL`,
  `LI_INFRA_USD_PER_RUN`). The heuristic provider makes no model call, and the
  sources are free keyless APIs. A component with no configured rate is listed
  in `unpriced_components`, and `fully_priced` is false; it is never counted
  as zero.

Both carry `"kind": "estimate"` and `"measured": false`.

**The ceiling is a call-count containment.** Before any upstream request, every
research call reserves the worst-case platform-price allocation ($2.00)
against the global ceiling. The default ceiling is $10.00 per 86,400 s, so the
default configuration allows exactly **5 research calls per rolling 24 hours**
(`floor(10 / 2) = 5`), across every client and instance. A call that later
fails (a source failure or the time bound) still counts. A clarification-only
answer reserves nothing. In general the configuration allows
`floor(LI_TRIAL_SPEND_CEILING_USD / 2) * ceil(86,400 / LI_TRIAL_SPEND_WINDOW_SECONDS)`
research calls per day; `research_calls_per_day()` computes it.

What the default configuration allows per day:

| What | Per day (defaults) | Scope |
|---|---|---|
| Research calls (`trial_research`, `trial_verify_claim`, `trial_compare`) | **5** | global |
| Upstream HTTP requests to sources | **at most 5** (1 per research call) | global |
| Research calls running at once | **at most 2** | global |
| Tool calls, clarification-only answers included | 240 per client IP (10 per hour) | per IP |
| HTTP requests to `/mcp-trial` | 43,200 per client IP (30 per minute); 864,000 in total (600 per minute) | per IP; global |

## Admission, concurrency and the ceiling

All admission state is in the database, so it holds across serverless
instances. Every control **fails closed**. A store that is unconfigured,
unreachable, times out (5 s) or answers anything but the expected type
refuses the request. There is no in-memory fallback, even with
`LI_RATE_LIMIT_BACKEND=memory`.

| Control | Store | Default | Env override |
|---|---|---|---|
| Requests per client IP (HTTP, every trial request) | `trial_ip` bucket | 30 / minute | `LI_TRIAL_IP_REQUESTS_PER_MINUTE` |
| Requests, global | `trial_global` bucket | 600 / minute | `LI_TRIAL_GLOBAL_REQUESTS_PER_MINUTE` |
| Tool calls per client IP | `trial_call_ip` bucket | 10 / hour | `LI_TRIAL_IP_CALLS_PER_HOUR` |
| Research calls running at once, global | `li_trial_slots` (`li_acquire_trial_slot`) | 2 | `LI_TRIAL_MAX_CONCURRENT` (1 to 10) |
| Operator-wide ceiling, in platform-price dollars | `trial_spend` bucket | $10.00 / 86,400 s | `LI_TRIAL_SPEND_CEILING_USD`, `LI_TRIAL_SPEND_WINDOW_SECONDS` (60 to 86,400) |

A research call is admitted in this order: per-IP tool-call allowance,
clarification gate, plan bounds, **concurrency slot**, **ceiling reservation**,
and then the one upstream request. A refused slot reserves nothing from the
ceiling. A refused reservation releases the slot.

**Concurrency slots** (`supabase/migrations/20261011120000_li_trial_slots.sql`).
`li_acquire_trial_slot(slot_id, max, lease)` deletes expired slots and inserts
one only while fewer than `max` unexpired slots exist. It runs under a
transaction-scoped advisory lock, so two instances can never both take the
last slot. The worker releases its slot (`li_release_trial_slot`) when it
ends, whether it succeeded or failed. A slot whose instance died is reclaimed
when its lease expires. The lease (60 s) exceeds the 40 s call bound.

Tests:

- Six parallel calls through six separate app instances that share one store never put more than 2 requests in flight at the upstream server.
- Six parallel calls under a $4 ceiling admit exactly 2.
- The real-PostgreSQL proof runs concurrent acquisitions over several connections on PostgreSQL 16. It checks the count, release, lease reclaim and the refusal of invalid arguments.

Refusals:

- An HTTP limit returns `429 rate_limited` with `Retry-After`.
- A tool-call allowance returns `TRIAL_RATE_LIMITED`.
- When every slot is in use, the call returns `TRIAL_BUSY`; nothing ran and nothing was reserved.
- An exhausted ceiling returns `TRIAL_CEILING_REACHED`, and nothing runs.
- A store that is unconfigured, unreachable or slow, or that answers in a malformed way, gives `503 temporarily_unavailable` at the HTTP layer, or `TRIAL_UNAVAILABLE` during a call.
- An invalid configuration value also gives `TRIAL_UNAVAILABLE`. A ceiling of `0` disables trial research.

## Client address, keyed hashing and shared egress

Per-IP limits need a client address. How it is read depends on the host:

- **On Vercel** (`VERCEL=1`, or `LI_TRIAL_TRUSTED_PROXY=vercel`): the first
  address in `x-vercel-forwarded-for`, else in `x-forwarded-for`. Vercel's
  request-header documentation (vercel.com/docs/headers/request-headers,
  checked 2026-10-11) says that Vercel overwrites `X-Forwarded-For` and does
  not forward external IPs, to prevent spoofing. It also says that
  `x-vercel-forwarded-for` is identical but survives a proxy placed in front
  of Vercel, hence that order. A missing or unparsable value refuses the
  request.
- **Anywhere else**: the socket peer only. There, `x-forwarded-for`,
  `x-vercel-forwarded-for`, `x-real-ip` and the header named by
  `LI_CLIENT_IP_HEADER` are client-supplied, and they are never trusted by the
  trial. `LI_TRIAL_TRUSTED_PROXY=vercel` outside Vercel is a misconfiguration
  and refuses every request. `LI_TRIAL_TRUSTED_PROXY=none` turns header trust
  off even on Vercel.

IPv6 clients are keyed by their /64. IPv4-mapped IPv6 addresses are keyed as
IPv4.

**Keyed hashing.** The per-IP digests are
`HMAC-SHA256(LI_TRIAL_IP_HMAC_KEY, "<bucket>:<ip>")`. Without the key, or with
a key under 32 characters, the trial refuses every request rather than store
reversible digests. Rotating the key resets every per-IP window. Global
buckets use the constant key `operator`, hashed with SHA-256, and contain no
client data.

**IP is not a user.** Many people share one address. Assistant platforms such
as ChatGPT call MCP servers from shared egress addresses, and NAT, carrier
networks, offices and VPNs do the same. A per-IP limit is therefore a coarse
abuse damper: it may throttle many ChatGPT users at once, and it never
identifies anyone. The containment that matters (the ceiling, the concurrency
bound and the global request limit) does not depend on the client address.
Tests show that rotating addresses on Vercel does not get past it.

## Source failures, receipts and output

- A retrieval that fails (HTTP error, timeout, redirect, oversized body, refused URL or malformed JSON) is reported as a failure. The call returns an error result, `TRIAL_SOURCE_FAILED`, naming the source and the reason. It is never an empty success. The call still counts against the ceiling.
- A partial retrieval (some records, then a problem) succeeds with `retrieval.outcome: "partial"` and a `warnings` entry.
- The research receipt is verified with `verify_receipt` before it is returned, and the discovery receipt of `trial_compare` with `verify_discovery_receipt`. A receipt that does not verify refuses the call (`TRIAL_RECEIPT_INVALID`).
- The output bound sheds re-derivable artifacts first and never the receipts.

## What is stored

- Rows in `li_rate_limit_events`, written by `li_take_keyed_rate_limit`: `bucket` (`trial_ip`, `trial_global`, `trial_call_ip` or `trial_spend`), `key_hash` (the HMAC above for per-IP buckets, SHA-256 of `"<bucket>:operator"` for global ones) and `created_at`. Rows outside their window are deleted on the next take for that key, and an opportunistic prune removes any row older than one day.
- Rows in `li_trial_slots`: a random slot id, `acquired_at` and `expires_at`. A row is deleted on release or once expired.

Raw IPs, questions, results, session ids and tokens are never stored.

*Limitation:* the OAuth and activation limiters outside the trial still store
unsalted SHA-256 IP digests. This change does not alter them.

Request telemetry is the existing content-free structured log line (method,
path, status, duration, request id). It contains no IP or body.

## How ChatGPT connects

1. Deploy the dedicated MCP surface with `LI_TRIAL_ENABLED=true`, a configured store with both migrations applied, and `LI_TRIAL_IP_HMAC_KEY` in the host's secret store.
2. In ChatGPT (developer mode, add a connector or app), enter `https://<mcp-origin>/mcp-trial` with no authentication.
3. ChatGPT initializes, lists the three `noauth` tools and can call them anonymously.
4. For Cases, durable research, history and the full tool set, connect `https://<mcp-origin>/mcp` with OAuth as described in `docs/PUBLIC_MCP.md`.

## Not verified

**The real ChatGPT installation test has NOT been done.** No ChatGPT connector
has been installed against `/mcp-trial`, and no ChatGPT session has called the
trial tools. The repository verifies the following only with tests:

- the HTTP and JSON-RPC behaviour
- the `securitySchemes` placement
- the bounds and the fail-closed abuse controls, against fake upstream servers on 127.0.0.1
- the concurrency slots on a real PostgreSQL 16 server (CI `postgres-proof`), not on Supabase
- the real pipeline on fixtures

The current OpenAI documentation was consulted for the `securitySchemes`
placement. ChatGPT's handling of a separate noauth connector beside an OAuth
connector has not been observed. The Vercel header behaviour comes from
Vercel's documentation and is tested with simulated headers; it has not been
observed on a Vercel deployment of the trial. No hosted deployment of the
trial exists.
